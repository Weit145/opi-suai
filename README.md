# opi-suai

Учебный проект по дисциплине «Основы программной инженерии» (ГУАП, группа 4431,
вариант 34): информационная система фирмы по сборке и продаже компьютеров и
комплектующих.

Репозиторий содержит инфраструктуру этапа I лабораторной работы № 2 и задел
для следующей лабораторной работы (этап II):

1. инфраструктуру этапа I — виртуальную машину с Redmine и модель работ проекта;
2. задел этапа II — учебный web-сервис оформления, оплаты, сборки и
   доставки заказов.

Итоговый отчёт: [docs/ОПИ_ЛР2_отчёт_вариант_34.docx](docs/ОПИ_ЛР2_отчёт_вариант_34.docx)
(копия в PDF: [docs/ОПИ_ЛР2_отчёт_вариант_34.pdf](docs/ОПИ_ЛР2_отчёт_вариант_34.pdf)).

## Структура репозитория

| Каталог | Назначение |
|---|---|
| `vm/` | управление QEMU/KVM-машиной с Ubuntu 24.04 и Redmine |
| `lab/` | требования и сценарий автоматического наполнения Redmine |
| `cmd/app/` | HTTP API и точка входа миграций |
| `cmd/provider/` | учебный внешний симулятор платежей и доставки |
| `internal/app/` | обработчики, аутентификация, заказы, интеграции |
| `internal/domain/` | модель предметной области и правила совместимости |
| `migrations/` | схема PostgreSQL |
| `web/` | клиент на React + TypeScript + Vite |
| `deploy/` | Dockerfile, compose-файлы, nginx и локальные сертификаты |
| `docs/` | отчёт по лабораторной работе |

## Этап I. Виртуальная машина и Redmine

Отдельная Ubuntu 24.04 в QEMU/KVM с Redmine 6.1.5, PostgreSQL, nginx/Puma,
темой Bleuclair и Git. Redmine устанавливается из исходников внутри гостевой
ОС.

```sh
make vm-up      # запустить ВМ; при первом запуске создать и установить
make vm-seed    # заполнить Redmine проектом pc-assembly-34
make vm-status  # проверить состояние
make vm-ssh     # войти в Ubuntu внутри ВМ
make vm-down    # штатно выключить ВМ с сохранением данных
```

Redmine в ВМ: http://localhost:8082. Логин `admin`, сгенерированный пароль
сохранён в локальном файле `.vm/credentials.txt`. При первом запуске дождитесь
окончания установки (`make vm-logs`).

Проект `pc-assembly-34` наполняется скриптом `lab/setup_redmine.rb` по
описанию `lab/project.json`: 38 задач, три участника, роли, трекеры, статусы и
переходы workflow. Учётные данные участников находятся в локальном файле
`.vm/team-credentials.json` и не попадают в репозиторий.

Наполнение отделено от установки. После того как ВМ впервые загрузилась и
появилось сообщение `READY`, выполните `make vm-seed`. Команда загрузит
`lab/project.json` и `lab/setup_redmine.rb` в ВМ, выполнит сценарий через Rails
runner и сохранит пароли участников в `.vm/team-credentials.json`. Повторный
запуск безопасен: существующие записи обновляются, новые создаются, пароли уже
существующих пользователей не сбрасываются.

Чтобы развернуть те же данные на другом ПК, склонируйте репозиторий, выполните
`make vm-up`, дождитесь `READY`, затем выполните `make vm-seed`. Если нужны те
же пароли участников, что и на исходной машине, скопируйте
`.vm/team-credentials.json` в такой же путь до запуска `make vm-seed`; иначе
пароли будут сгенерированы заново. Пароль администратора `admin` от этого файла
не зависит: он создаётся при установке ВМ и хранится в `.vm/credentials.txt`.

Подробности, команды для отчёта и отличия от методички: [vm/README.md](vm/README.md).

## Этап II. Приложение

### Стек

- Go 1.25, `chi`, `pgx/v5`, `validator`;
- PostgreSQL 16;
- React 19, TypeScript, Vite;
- nginx с TLS для frontend;
- Docker Compose для сборки и запуска;
- учебный платёжный/доставочный провайдер `cmd/provider` как внешняя система.

### Запуск

```sh
make app-init   # создать .env.app и локальные TLS-сертификаты
make app-up     # собрать образы и поднять db, migrate, backend, provider, frontend
make app-logs   # смотреть журналы
make app-down   # остановить стек
```

Интерфейс: https://localhost:8443 (HTTP-порт 8083 перенаправляет на HTTPS).
Сертификат самоподписанный, поэтому браузер предупредит о неизвестном центре
сертификации. Секреты генерируются в `.env.app` и не выводятся в консоль.

Демонстрационные учётные записи: `customer@lab.invalid`,
`manager@lab.invalid`, `warehouse@lab.invalid`, `assembler@lab.invalid`,
`admin@lab.invalid`. Общий пароль хранится в переменной `DEMO_PASSWORD`
файла `.env.app`.

### Тесты

Модульные и приёмочные тесты Go требуют отдельную базу PostgreSQL с суффиксом
`_test`; строка подключения передаётся в `TEST_DATABASE_URL`. Скопируйте
`deploy/test.env.example` в `.env.test`, заполните значения и выполните:

```sh
make test
```

Скрипт `deploy/run-tests.sh` читает `.env.test` и запускает `go test -race ./...`.
Приёмочные тесты проверяют конкурентное резервирование последней единицы
товара, фиксацию цен, откат транзакции, повторную обработку платежного
события, возврат после неудачной сборки и правила совместимости.

Проверка клиента:

```sh
cd web
npm ci
npm run build
```

Сквозные проверки выполнялись в Chromium, Firefox и WebKit: каталог, поиск,
адаптивная вёрстка 360 px, вход, ротация refresh-токена, конфликт
совместимости, оформление заказа, оплата через внешний симулятор, склад,
доработка сборки, доставка и завершение заказа. Результаты и скриншоты
приложены к отчёту в `docs/`.

## Архитектура

`cmd/app` — модульный монолит: REST API, транзакционное оформление заказа,
резервирование остатков, фиксация цены, идемпотентная обработка платежных
событий, задания на сборку, отгрузки и уведомления. `cmd/provider` имитирует
внешние платёжную и доставочную системы и подписывает callback-запросы общим
секретом. `internal/domain` содержит правила совместимости компонентов.
`web` — SPA, которая работает с API и отображает каталог, конфигуратор,
корзину, заказы и служебные экраны ролей.

Схема данных описана в `migrations/001_initial.sql`; предусмотрены ограничения
целостности, запрет отрицательных остатков и журналирование переходов статусов.
