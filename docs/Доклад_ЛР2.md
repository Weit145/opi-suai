## Ответы на вопросы руководителя

**1. Какие атрибуты являются ключевыми для формирования модели работ по проекту?**

Ключевые атрибуты модели работ: цель и ожидаемый результат; декомпозиция через родительскую задачу; трекер; статус; приоритет; исполнитель; автор; проект и версия; описание с критерием приемки; плановые даты начала и завершения; оценка трудоемкости; процент готовности; связи и подзадачи; наблюдатели. В нашем проекте дополнительно важны роль исполнителя и матрица разрешенных переходов, потому что они определяют, кто и когда может изменить состояние задачи.

**2. От каких параметров модели работ зависит жизненный цикл задачи?**

Жизненный цикл зависит от трекера, текущего статуса, роли пользователя и его прав, назначенного исполнителя и автора, а также от настроенных переходов workflow. На него влияют проект, приоритет, сроки, зависимости и подзадачи, результаты проверки и необходимость доработки. В нашем Redmine базовый маршрут — «Запланирована → Назначена → В работе → На контроле», а закрытие, возврат и отмену выполняет только руководитель.

**3. Опишите ролевую модель, разработанную под вариант.**

В проекте Redmine три роли. Руководитель проекта управляет проектом, участниками, версиями, категориями и связями задач, закрывает, возвращает и отменяет задачи. Специалист по ИС и DevOps-инженер имеют базовые права на задачи, wiki, файлы и репозиторий, а также управляют подзадачами. Встроенные роли «Менеджер», «Разработчик» и «Репортер» в проекте не назначены. Служебная учётная запись администратора используется только для настройки Redmine.

**4. Почему в отчёте рассматривается только этап I?**

В методических указаниях задание сформулировано для двух этапов, но в настоящей работе выполнен этап I — организация технологического процесса. Реализация информационной системы относится к следующей лабораторной работе; задачи этапа II включены в дерево работ как план, но в отчёте не заявляются как выполненные.

## Ответы специалиста по информационным системам

**1. На каких технологиях разработана система управления проектами на базе Redmine?**

Redmine — web-приложение на Ruby on Rails. Используются Ruby, ActiveRecord, Rack, сервер приложений Puma или Passenger, HTML/ERB-шаблоны, JavaScript, REST API и система плагинов. В нашей ВМ установлены Ruby 3.2.3, Redmine 6.1.5, Puma и nginx; данные хранятся в PostgreSQL 16.

**2. С какими СУБД Redmine поддерживает интеграцию?**

Redmine поддерживает PostgreSQL, MySQL/MariaDB и SQLite; для Microsoft SQL Server требуется отдельный адаптер. В учебной среде выбрана PostgreSQL 16.15: она обеспечивает транзакции, ограничения целостности и удобна для резервного копирования.

**3. Опишите схему web-приложения Redmine.**

Браузер обращается к nginx, который раздает статические файлы и проксирует запросы к Puma. Puma запускает Rack-приложение Ruby on Rails. Контроллеры обрабатывают запрос, модели ActiveRecord работают с PostgreSQL, представления ERB формируют HTML. Дополнительно доступны REST API, темы оформления и плагины. В нашей схеме nginx и Puma работают внутри виртуальной машины, а PostgreSQL — отдельная служба.

## Ответы DevOps-инженера

**1. К какому виду систем контроля версий относится Git?**

Git — распределенная система контроля версий (DVCS). Каждый клон содержит полную историю, поэтому работа возможна локально, а сервер не является единственной точкой отказа. Обмен изменениями выполняется через push и pull.

**2. Какие модели применения системы контроля версий Git Вам известны?**

Известны централизованная модель с общей веткой, feature-branch, Git Flow, GitHub Flow, GitLab Flow, trunk-based development и модель fork/pull request. Выбор зависит от размера команды, частоты релизов и требований к стабильности.

**3. Опишите модель Git Flow.**

Git Flow использует main для стабильных релизов и develop для интеграции. Функциональные ветки feature/* создаются от develop и вливаются обратно. Релизная ветка release/* стабилизирует версию и вливается в main и develop; hotfix/* создается от main для срочного исправления и вливается в main и develop. Релизы отмечаются тегами. В нашем репозитории эта модель применена для версий v0.1.0 и v0.1.1; ветка с инфраструктурой виртуальной машины влита в main.
